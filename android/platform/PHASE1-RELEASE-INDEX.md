# Phase 1 aggregate release-evidence index

`android/tools/phase1_release_index.py` is the final Phase 1 gate. It replays
the producer verifiers, cross-binds their exact outputs, and creates one
deterministic `phase1-release-index.json`. The SHA-256 printed by `create` is
the out-of-band trust anchor. A digest by itself never turns an unchecked
record into test, source, signing, or release evidence.

The gate accepts production evidence only. The x86 sibling remains explicitly
development-only; it can establish source-matched emulator behavior but cannot
qualify ARM artifacts. A diagnostic runtime run, development client record,
unsigned ARM artifact, incomplete upstream coverage, prose-only signing claim,
implicit channel operation, untriaged defect, or incomplete review fails.

## Policy-free runtime admission is currently blocked

The current `runtime_result`/four-control-record assembly slot and
`run_phase1_runtime_qualification.py` replay are historical product-policy
DesktopService/Haskell machinery. Their passing status does **not** prove the
genuine policy-free `org.wonad.desktop` ConformanceService runtime required by
Phase 1. Existing strict checks remain, but `create` and `verify` now fail at
the final publication edge until the reviewed complete policy-free producer,
independent raw auditors and aggregate bindings are integrated. No index PASS,
environment/CLI waiver, relabelled report or shortened run is available.

The implemented policy-free three-clean-boot aggregate is separate evidence:
three distinct ordinary guests, three mixed-size/density monitors and twenty
populated connector disconnect/reconnect cycles per boot. Its explicit
`passed_three_clean_boots_not_runtime_qualified` status cannot replace the
separate uninterrupted 86400-second soak with at least three complete rounds
of all nine original scenarios: hotplug, credential-sleep lock/unlock,
credential-key lock/unlock, user switch, frozen-client expiry/recovery,
SystemUI death, client death, same-signer APK update/restoration and malformed
calls. A bounded hotplug/continuous-health slice is not that soak; its full
campaign raw auditor currently remains unimplemented.

Before replacing the blocker, the final adapter must independently replay
the complete original 23 failure gates, policy-free three-boot raw evidence
and full-duration/minimum-round/all-nine-disturbance raw soak evidence. It
must bind the actual conformance APK/service, source/SDK/OS/image/packet
identities, live instrumentation/raw outputs, genuine consent, task/activity/
display incarnations, focus/input/pixels/stock-chrome absence, phone recovery,
four protected OS process epochs including Phone plus the client, and both
per-incarnation and cumulative resource bounds. API and Recents remain
mandatory separate fresh lanes with no shared guest/userdata/incarnation.

The legacy assembly/example below describes retained historical structure,
not an approved complete policy-free admission schema or permission to reseal
historical product reports. The transition deliberately invents no future
full-campaign kind while its producer/auditor contract is still incomplete.

## Evidence tree and path rules

Use one canonical absolute, non-symlinked evidence root. The assembly is its
literal direct child. Every assembly path is a canonical relative path below
that root. Links, special files, duplicate JSON keys, empty evidence,
private-key-like suffixes, and known private-key headers fail closed.
Production private keys never enter this tree.

Runtime producer records contain absolute paths. For the aggregate, the
runtime `admission.json`, frozen input plan, qualification, and
`evidence-index.json` must all be ordinary canonical files inside this same
root. Their recorded SHA-256 values and their bytes are rebound into the final
review. `verify` intentionally replays the original runtime verifier, so the
published tree must be installed at the absolute location sealed by those
producer records (or those records must be regenerated by a fresh campaign).
An external absolute runtime path is not accepted.

The mandatory inputs are:

- repository-exact `android/grapheneos.lock.json` and
  `android/EXTERNAL-SHELL.md`;
- x86 baseline/custom receipts, exact comparison, production runtime result,
  and the four embedded runtime control records above;
- ARM baseline/custom receipts and comparison;
- signed predecessor/successor release-pair receipt, both endpoint release
  trees including the successor's complete source provenance, public AVB/OTA/
  factory anchors, and independently authenticated otatools manifest;
- production client record, compile receipt, signed conformance APK, public
  signer certificate, exact `apksigner`, and complete SDK publication;
- the exact x86 product directory and source-matched development client packet,
  plus independently audited, stopped fresh guests for full API conformance
  and the phone-Recents external-display workflow;
- a signer-only x86/ARM source-difference proof when their APK signers differ;
- generic GrapheneOS-host, AOSP-host, and AOSP-emulator regression evidence;
- the repository-exact reviewed Atest plan, baseline run, custom run, and exact
  comparison described in
  [`PHASE1-UPSTREAM-TESTS.md`](PHASE1-UPSTREAM-TESTS.md);
- a public structured signing-ceremony record, structured custody
  observations, all public signer identities, and an exact copy of
  [`PHASE1-SIGNING-CEREMONY.md`](PHASE1-SIGNING-CEREMONY.md);
- a structured candidate-channel/operations record and exact copy of
  [`PHASE1-INSTALL-UPDATE-RECOVERY.md`](PHASE1-INSTALL-UPDATE-RECOVERY.md);
- final review, defect register, and every report they reference.

## Fresh API and Recents acceptance

The two `conformance_acceptance` reports are mandatory and cannot be replaced
by the long runtime campaign. They use separate newly created userdata,
containers, boots and run tokens, while sharing one immutable derived
conformance image, exact custom x86 product and exact development packet. The
derived image's base must be the image selected by the production runtime
campaign. Its embedded baseline/custom/comparison receipt identities, source
pin, fingerprint, custom product path, packet receipt and development signer
must match the selected x86 build evidence exactly.

The API report is replayed by `phase1_conformance_acceptance.py`. Its auditor
requires initially absent target packages, normal non-replacement installs,
ordinary SystemUI consent rather than a seeded setting, full v3 operation,
callback, capability and facade coverage, exact running OS/APK bytes, stable
protected-process epochs, cumulative protected crash/ANR evidence, and an
exact stopped owned container. It remains expressly narrower than runtime or
hardware qualification.

The Recents assembly path selects the outer report from
`run_phase1_conformance_recents_guest.py`, not only the child report. The
independent `phase1_conformance_recents_guest_acceptance.py` auditor replays
the outer raw command journal, exact-image/product/packet validation, initial
package absence, owner-user/keyguard/consent actions, two state and byte
observations bracketing the child, cumulative event readback, and exact
teardown. The mounted state directory and its empty `tmp/` child are created
exclusively, observed and durably sealed immediately before launch; their
inode/ownership/mode identities and the exact reviewed wrapper/common source
bytes are independently replayed. It then independently invokes
`phase1_conformance_recents_acceptance.py` over the child raw task/window/input,
UI, pixel and display evidence. The child execution timeline must fit wholly
between the outer setup and terminal observations.

The aggregate rejects reuse between either fresh lane and any of the four
runtime campaign guests. API and Recents container IDs, boot IDs, run IDs and
userdata paths must differ; all run, boot and container identities must also
differ from every campaign record. The development packet's compile receipt,
source-freeze identity and unsigned conformance APK must match the production
SDK/client provenance, while its Wonad and conformance APKs retain the exact
x86 development signer. The development and production signed-payload digests
use different normalization schemas and are not compared; both producers must
instead prove derivation from the exact common unsigned APK. This intentionally
cross-binds source/API bytes without pretending a development signature is a
production one.

At the publication edge the aggregate rehashes every file declared by the API
report, the Recents guest report and the child Recents report. It also
revalidates and inventories the complete development-packet tree and rehashes
the exact selected product images and OS artifacts. Deterministic identities
for those five transitive inputs are part of the final review map and index, so
a later full verification detects mutation after either semantic auditor
returned; top-level report hashes alone are not treated as race closure.

No successful report currently exists merely because these inputs are listed;
both guests must be run afresh and their authenticated reports supplied before
the aggregate can pass.

`source_difference_proof` is `null` only when x86 and ARM use the same signer
and byte-identical stage marker. Otherwise create it from the authenticated
custom receipts:

```sh
python3 android/tools/phase1_release_index.py create-source-proof \
  --x86-custom-receipt /evidence/x86/custom-receipt.json \
  --x86-custom-sha256 "$X86_CUSTOM_SHA256" \
  --arm-custom-receipt /evidence/arm/custom-receipt.json \
  --arm-custom-sha256 "$ARM_CUSTOM_SHA256" \
  --output /evidence/x86-arm-source-difference.json
```

The proof requires the same lock, signed manifest/project ledger, checkout
materializations, and normalized schema-4 stage. Only
`signer_certificate`, `signer_sha256`, the three signer-generated files, and
the separately authenticated ARM Updater stage may differ. The signed ARM
successor is additionally required to carry source provenance matching the ARM
comparison's complete project ledger, owned/generated inputs, builder, repo
tool commit, and materialization ledger.

The release-index gate independently checks automatic-OTA eligibility as soon
as the authenticated pair and full endpoint receipts are loaded. Both full
receipts must have positive exact-integer build timestamps; the pair's embedded
endpoint labels and timestamps must match them, and the successor timestamp
must be strictly greater than the predecessor's. The same check applies to
direct release cross-binding validation. The pinned Updater uses this timestamp
comparison, not just a larger incremental build number. A same-source successor
therefore requires an explicitly selected, recorded `WONAD_BUILD_DATETIME`
greater than the predecessor's timestamp; the release-driver default manifest
commit time does not advance merely because the build number does. This does
not claim that any signed pair or physical OTA has been executed. The frozen
pair producer still permits equal timestamps until its own safe tool/source/
provenance update; standalone pair verification cannot bypass this index gate.

## Upstream evidence

Two independent evidence classes are required; neither replaces the other.

The generic record kind is
`wonad-phase1-upstream-regression-evidence`, schema 2. It binds a copy of the
exact repository-reviewed generic plan and one baseline/custom native receipt
pair per coverage class. Each `runs` row contains only `class`, `baseline`, and
`custom`; each side is an ordinary `{path, sha256, size}` reference. It cannot
contain an operator command, a manually claimed failure list or a hand-written
JUnit report. The aggregate independently replays the native producer, its
raw results and isolation/source/build evidence with full live reauthentication,
then cross-binds the exact selected x86 build receipt bytes and source pin.

AOSP host results use the fixed source-pinned Soong/Blueprint native Go JSON
plan; AOSP emulator results use schema-2 isolated Atest. Shared cases cannot
worsen (`passed` < `skipped` < `failure` < `error`), and only the thirteen reviewed
passing custom WmTests additions are allowed. GrapheneOS-host applicability
requires bounded pinned-source evidence rather than relabeling an unrelated
suite. The source audit found no declared applicable host module; its native
applicability producer independently replays exact reviewed inventories and
explicitly records `tests_executed: false` in the comparison. Applicable Secure Paste tests
run on the emulator as required coverage, never as a host-test claim.

Create the generic envelope with `create-upstream-record`; do not hand-author
a passing result. Its selection JSON has only `schema: 1`,
`kind: "wonad-phase1-native-upstream-selection"`, the reviewed `plan` reference,
`builds` containing exact baseline/custom receipt references, and the three
native `runs` pairs described above. All paths are canonical relative paths
beneath the evidence root, and all references include exact SHA-256 and size.

```sh
python3 android/tools/phase1_release_index.py create-upstream-record \
  --evidence-root /absolute/phase1-evidence \
  --selection /absolute/phase1-evidence/tests/upstream-selection.json \
  --output /absolute/phase1-evidence/tests/host-regression.json
```

The producer replays both selected OS builds and every native coverage gate
before publishing, rechecks all selection anchors at publication, and refuses
an existing output. All record/index creation uses same-directory temporary
files: validate the write count and owned-file size/digest, file-fsync the
complete bytes, atomically link without replacing
an existing output, remove the owned temporary, and fsync the parent directory.
The final inode and bytes are rechecked before returning the digest. A
post-publication durability/verification failure is reported but never deletes
the complete published record or a competing replacement. Twelve focused
publication tests cover incomplete/short writes, temporary corruption, fsync
and ownership-observation failures, concurrent output creation and inode/byte
replacement; all 71 release-index host tests pass. An unobservable temporary
inode is preserved rather than deleted on a guessed ownership basis.
An unresolved applicability gate, missing test execution,
new/worsened case, source/toolchain mismatch or incomplete producer fails
before the record is created. This command is implemented and host-tested;
no complete native regression envelope has yet been produced.

Separately, the aggregate requires the exact repository plan
`phase1-upstream-tests-2026100600.json` and replays
`phase1_upstream_test_comparison.py` over its baseline/custom run receipts. It
cross-binds those runs to the exact x86 baseline/custom build receipt bytes and
source pin and requires all six reviewed suites, the exact four GrapheneOS
Secure Paste cases, and no new or worsened case.

## Public signing ceremony

The ceremony record kind is `wonad-phase1-signing-ceremony-record`. It selects
the exact release, source identity, predecessor/successor build numbers, and a
positive UTC interval of no more than 72 hours. It identifies three distinct
accountable parties: release operator, key custodian, and independent verifier.
Its policy reference must be byte-identical to
`PHASE1-SIGNING-CEREMONY.md`.

All custody booleans in the record must be true, but booleans and prose are not
proof by themselves. Each preflight, postflight, and backup/restore attachment
must be JSON kind `wonad-phase1-signing-custody-observation` with exact fields:

```json
{
  "schema": 1,
  "kind": "wonad-phase1-signing-custody-observation",
  "qualification": "production",
  "release": "2026100600",
  "product": "frankel",
  "category": "preflight",
  "observed_utc": "2026-10-10T10:10:00Z",
  "observer": {"name": "accountable name", "contact": "mailto:address@domain"},
  "predecessor_build": "ten digits",
  "successor_build": "ten digits",
  "release_pair_sha256": "64-lowercase-hex",
  "wonad_signer_sha256": "64-lowercase-hex",
  "controls": ["the exact category-specific controls required by the validator"],
  "result": "passed_observed_signing_custody_controls"
}
```

The observation time must fall inside the ceremony. Preflight is attributed to
the release operator, postflight to the independent verifier, and backup/
restore to the key custodian. The three report sets must be non-empty and have
distinct byte hashes. Arbitrary prose is rejected.

The exact sorted controls are:

- preflight: `build_container_removed_before_signing`,
  `core_dumps_disabled`, `hibernation_disabled`, `networking_disabled`,
  `offline_host`, `private_material_outside_source_build_and_evidence`, and
  `swap_disabled`;
- postflight: `independent_verification_host`,
  `locked_ram_temporary_material_removed`, and
  `public_release_pair_verified`;
- backup/restore: `restore_test_completed` and
  `two_geographic_encrypted_backups`.

The record also supplies the exact nine GrapheneOS public X.509 roles, the
distinct Wonad X.509 identity, RSA-4096 AVB public input, and Ed25519 factory
public input. The Wonad, OTA/releasekey, AVB, and factory identities are
cross-bound to the verified production client and signed release pair. Exact
release/signing/verifier tool hashes are recomputed from the reviewed checkout.
Each X.509 record's DER identity, subject and `algorithm` are parsed from one
hash/size-authenticated stable stdin snapshot, using pinned OpenSSL. No
subsequent parsing by mutable pathname can mix properties of another
certificate into that snapshot. Allowed keys are RSA-3072/4096 and ECDSA on P-256/P-384; an unsupported
size, curve or key family, a relabelled record, ambiguous output, certificate
drift or parser/tool failure is rejected. The certificate's signature
algorithm is not a substitute for its subject public-key algorithm.

## Candidate channel and operations

The operations record kind is `wonad-phase1-candidate-operations`. It must
select the authenticated pair and ARM Updater URL and identify a concrete
private channel. The update/metadata endpoint and artifact, index-digest, and
failure-communication endpoints must be non-example HTTPS locations outside
GrapheneOS ownership. It records signed OTA-package metadata, endpoint/pair
receipts, independently authenticated trust anchors, and offline-verification
controls. The `signed_ota_metadata` field refers to metadata authenticated as
part of the signed OTA, not a claim that stock channel text has its own
signature. The pinned Updater's plaintext channel files are delivered over
HTTPS; downloaded OTA packages are cryptographically verified. An operations
channel label is administrative, not an automatic client-channel selection.
Metadata and requested artifact paths must resolve from the configured
Updater base URL, even when artifacts are hosted separately.

It provides non-placeholder name/contact owners for release, channel, security
updates, GrapheneOS rebases, and withdrawal. Rollout is fixed to a private
allowlist, with production disabled until exact-hash Pixel 10 Phase 2
qualification. Withdrawal removes channel metadata and signed update artifacts
and publishes a signed notice. It monitors at least one official GrapheneOS source, reviews
security updates at most every seven days, makes a rebase decision at most
every 31 days, and sends required OS changes back through Phase 1.

Its change-control rule requires new Phase 1 and Phase 2 qualification for an
OS privileged-interface or signer change. An ordinary APK-only update may ship
independently only while API, OS trust policy, and signer are unchanged. The
record references the exact ceremony and the byte-exact install/update/recovery
runbook. It must state that physical rollback is untested and merely procedural
until Phase 2.

## Defects and final review

The defect register kind is `wonad-phase1-defect-register`. No `open` status is
accepted. Critical/high items must be resolved with immutable closure evidence.
Only medium/low items may be accepted, and then only with non-placeholder owner
and workaround. The final review binds the sorted complete defect ID set.

The final review kind is `wonad-phase1-final-os-glue-review`, with decision
`approved`, identified non-placeholder reviewers, and exactly these scopes:

```text
binder_lifecycle_and_cancellation
channel_operations_and_maintenance
display_containment_and_input
identity_and_signer_admission
language_and_unsafe_code
phone_ui_regression
privileged_interface_inventory
release_configuration
selinux_and_permissions
signing_ceremony_and_key_custody
source_and_toolchain_provenance
update_and_recovery
```

`evidence_sha256` has exactly 44 entries: lock/API; x86 receipts/comparison;
runtime result plus four embedded records; ARM receipts/comparison/pair and
four public release inputs; client record/source/APK/certificate/apksigner/SDK;
development packet receipt plus fresh API, outer Recents and child Recents reports,
the complete packet tree, selected product identity, and API/outer-guest/child
raw-evidence sets;
source-difference proof; generic upstream evidence plus Atest plan, both runs,
and comparison; signing ceremony/policy; operations/runbook; and defect
register. The aggregate recomputes the entire map. The review report itself is
transitively bound by the reviewed record.

## Create and verify

The output must be a fresh direct child named
`phase1-release-index.json`:

```sh
python3 android/tools/phase1_release_index.py create \
  --evidence-root /evidence \
  --assembly /evidence/phase1-assembly.json \
  --output /evidence/phase1-release-index.json
```

Record the printed digest independently. Offline verification authenticates
the index before parsing it, replays every semantic verifier and cross-binding,
and checks that the verifier bytes, reviewed lock, and API contract did not
change during collection:

```sh
python3 android/tools/phase1_release_index.py verify \
  --evidence-root /evidence \
  --index /evidence/phase1-release-index.json \
  --expected-sha256 "$PHASE1_RELEASE_INDEX_SHA256"
```

Success proves a complete Phase 1 **private flashable candidate evidence
freeze**. It does not claim a production rollout, physical Pixel 10 execution,
or tested physical rollback; those remain Phase 2.
