# Phase 1 production signing ceremony

This document fixes the signing roles and handling rules for the Phase 1 Pixel
10 (`frankel`) candidate. It does not create keys and is not ceremony evidence. Phase 1 is
blocked until a real ceremony produces the public identities and signed
predecessor/successor artifacts required by the release index.

## Required independent identities

Create one long-lived signing lineage for this project, with these roles:

- GrapheneOS package certificates: `bluetooth`, `gmscompat_lib`, `media`,
  `networkstack`, `nfc`, `platform`, `releasekey`, `sdk_sandbox`, and `shared`;
- a 4096-bit RSA AVB key and its `avb_pkmd.bin` public metadata;
- an Ed25519 factory-archive signing key; and
- one ordinary APK signing identity for `org.wonad.desktop`.

The Wonad APK identity must differ from every OS certificate. It is never the
platform key, never shares an Android UID, has exactly one current signer and
has no signing lineage. The selected public certificate SHA-256 is staged into
the ARM OS, signs the conformance APK, and remains the APK identity through
later independently shipped Wonad updates. Changing it requires a new OS image
and complete Phase 1/2 requalification.

The x86 development sibling may use its existing development APK signer only
when the aggregate gate proves that the x86 and ARM staged sources differ
exhaustively in signer-generated bytes and ARM-only Updater configuration. A
development signer is never accepted by an ARM production receipt.

## Ceremony host and custody

Use a dedicated offline signing host booted from authenticated media. Disable
networking, swap, hibernation and core dumps before private material is
available. Production must not use the `WONAD_SIGN_WITH_ACTIVE_SWAP` override.
Mount the key store from encrypted removable storage outside both the GrapheneOS
and Wonad checkouts. Decrypted temporary material, when required by upstream
signing tools, belongs on locked RAM-backed storage and must be removed before
the host is powered down.

Use three accountable, distinct roles:

- the release operator authenticates sources, receipts, build evidence and the
  requested predecessor/successor build numbers; and
- the key custodian unlocks signing material only after those checks pass.
- the independent verifier observes postflight cleanup and verifies the public
  signed release pair on a separate host.

Keep at least two encrypted, geographically separate backups. Record restore
tests without recording a passphrase, private key, key-store path, token PIN or
recovery secret. A lost or suspected-compromised OS, AVB, factory or Wonad key
withdraws the channel; it is not repaired by silently substituting a key.

## Generation

Generate OS and AVB keys with the authenticated `script/generate-keys` from the
exact pinned GrapheneOS source. It emits encrypted PKCS#8 keys and the AVB
public metadata used by the upstream release tooling. Generate the factory
Ed25519 identity on the same offline host. Generate the Wonad identity
separately, preferably with a hardware-backed or offline keystore supported by
`apksigner`; only its public X.509 certificate enters the build host.

Do not copy AOSP test/debug keys, reuse GrapheneOS's keys, use a certificate
from the development packet, or generate keys inside a build container. Do not
put private material beneath either source checkout, Docker context, release
tree or evidence tree.

After generation, independently export and authenticate only:

- all ten X.509 public certificates (the nine OS roles plus Wonad);
- `avb_pkmd.bin`;
- the factory Ed25519 public key; and
- a public ceremony record identifying algorithms, public SHA-256 values,
  source pin, tool hashes, operators, UTC start/end times and result.

No private-key filename or storage location belongs in public evidence.

The aggregate does not accept this policy, free-form notes, or bare boolean
attestations as proof that the ceremony happened. Retain public structured
preflight, postflight, and backup/restore observations. Each observation must
identify its accountable observer and UTC time, bind the exact predecessor,
successor, release-pair SHA-256 and Wonad signer SHA-256, enumerate the exact
category-specific controls, and report
`passed_observed_signing_custody_controls`. Preflight is attributed to the
release operator, postflight to the independent verifier, and backup/restore
to the key custodian. Their schema is fixed by
[`PHASE1-RELEASE-INDEX.md`](PHASE1-RELEASE-INDEX.md); arbitrary prose fails.

## Build/sign boundary

Build unsigned target files without access to release keys. Preserve the exact
successful build container and its bind/log evidence until
`release-build.sh sign` performs its final preflight. That action must remove
and prove absence of the source-mounted build container before linking the
external key directory into the source for upstream signing.

During signing, require:

- the exact source, build OUT, log, builder/source/client provenance and
  conformance inputs authenticated by the preflight;
- a production conformance APK signed once by the selected Wonad identity;
- every OS key pair and public export present without symlinks;
- no active swap and no unexpected process, mount or network connection; and
- fresh non-overwriting release destinations.

The predecessor and successor must use the same OS, AVB, factory, OTA, Wonad
and update-channel identities. Build numbers are ten decimal digits and strictly
increase. Generate both full releases before creating the incremental OTA.

## Independent public verification

Move only signed artifacts and public trust anchors to a separate verification
host. Authenticate receipt and otatools-manifest SHA-256 values out of band,
then run the full and pair verifiers described in
[`RELEASE-RECEIPT.md`](RELEASE-RECEIPT.md). Verify the conformance APK with the
receipted `apksigner`, require one current signer/no lineage, and compare its
certificate to both the staged OS pin and ceremony record.

The public ceremony record is acceptable only when the final aggregate release
gate cross-binds its identities to the ARM build receipt, signed successor,
client provenance, release pair and channel operations record. A written
ceremony plan, an encrypted key directory, or a successful signature alone is
not Phase 1 completion.
